# ADR-0001 学習の進捗はブラウザの localStorage を一次情報とする

- 状態：採用
- 日付：2026年8月29日

## 背景

試験日まで11週、週23時間の学習を管理する必要がある。管理したいものは4つある。

1. 単元ごとの完了状況
2. ドリルの正誤（どの論点を何回間違えたか）
3. 実際の学習時間（計画の週23時間に対する実績）
4. 学習中に気づいた疑問

このうち 1 は教材HTMLのチェックボックスとして既に存在し、`localStorage` に保存されている。2 は採点結果を画面に出すだけでリロードすると消える。3 と 4 は記録する場所がない。

一方、リポジトリには `学習カリキュラム.md` があるが、これは計画であって実績ではない。次のセッションで Claude が「どこまで進んだか」を知る手段がなく、毎回ゼロから推測している。

記録の置き場所は、ブラウザ（教材を実際に使う場所）とリポジトリ（Claude が読める場所）のどちらかを一次情報に決める必要がある。両方に書けば必ず食い違う。

## 決定

**ブラウザの `localStorage` を一次情報とする。** リポジトリの `進捗ログ.md` はそこからの書き出しであり、両者が食い違ったときは `localStorage` を正とする。

書き出しは手動で行う。`progress.html` のボタンで `localStorage` の内容を JSON としてクリップボードにコピーし、それを Claude に渡して `進捗ログ.md` へ転記させる。

エクスポートは常に全期間を出力し、差分は取らない。転記時にどこから追記するかは、`進捗ログ.md` の最終記録日を見て Claude が判断する。

## 理由

**記録は発生した場所に置くのが最も壊れにくい。** ドリルを解くのも、時間が経過するのも、疑問が浮かぶのもブラウザの中である。ここで記録すれば、学習者は記録のための操作を何もしなくてよい。リポジトリを一次情報にすると、学習のたびに「Claude に報告する」という別の作業が発生し、これは必ず抜ける。抜けた記録は復元できない。

**Markdown を一次情報にすると、機械が読めるものが失われる。** ドリルの正誤を設問単位で持てば「直近2週間で3回以上間違えた論点」を機械的に取り出せる。散文で書かれた振り返りからは取り出せない。誤答の集計は、この教材で最も価値のある機能になりうる。

**それでも Markdown 側を残すのは、localStorage が消えるからである。** ブラウザのデータ削除、別デバイス、シークレットウィンドウ——いずれでも記録は消える。11週間ぶんの学習履歴を消える場所だけに置くことはできない。`進捗ログ.md` は git で管理されるバックアップであり、同時に人間が読み返す振り返りでもある。

**同期を自動化しない。** GitHub Pages は静的ホスティングであり、ブラウザからリポジトリへ書き込む経路がない。API トークンをクライアントに置けば書けるが、公開サイトに書き込み権限を晒すことになる。手動コピーは1回15秒で済み、この規模の学習記録には十分速い。

## 結果

- 学習記録の追加は `progress.html` を経由する。単元HTMLの著者が記録用のコードを書くことはない
- `進捗ログ.md` は Claude が書く。人間が直接編集してもよいが、次のエクスポートで上書きされることはない（追記型のため）
- `localStorage` が消えた場合、`進捗ログ.md` に転記済みの範囲までは復元できる。転記していない範囲は失われる。エクスポートは週1回以上行う
- 記録の配線が切れても画面には何も現れないため、品質ゲート8（進捗記録の健全性）で機械的に検査する

## 検討した代替案

**リポジトリの Markdown を一次情報とし、サイトは表示のみ。** 記録のたびに Claude との対話が必要になる。学習の合間に毎回それを挟むのは続かない。

**両者を独立に併存させ、同期しない。** 実装は最も軽いが、「今週何時間やったか」を知るのにブラウザを見て、「何が弱いか」を知るのに Markdown を見る、という分裂が起きる。どちらも不完全なまま残る。

**Markdown を一次情報とし、ビルド時に JSON へ変換してサイトへ配信する。** 表示は正確になるが、記録の発生場所（ブラウザ）から一次情報（Markdown）への経路が手動のままなので、上の1つ目と同じ問題を抱える。
