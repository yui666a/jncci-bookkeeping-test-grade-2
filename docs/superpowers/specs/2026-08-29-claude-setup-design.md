# 日商簿記2級教材プロジェクト Claude Code セットアップ設計

作成日：2026年8月29日

## 1. 目的

教材制作を、人手の注意力に頼らずに回す。

`教材制作ルール.md` は公開前の品質ゲートを8項目定めているが、現状はすべて人手で確認している。教材は1単元あたり50〜130KBのHTMLで、仕訳ドリルは1単元に25問入る。W1以降は毎週23時間ぶんの教材を作るため、目視での検算は早晩破綻する。

そこで、**答えが一意に決まる検査は機械に、判断が要る検査はサブエージェントに**振り分け、両者を1つの手順に組み込む。

## 2. 全体構成

```
簿記2級教材/
├── CLAUDE.md
├── .claude/
│   ├── agents/

│   │   ├── boki-drill.md
│   │   ├── boki-reviewer.md
│   │   └── boki-coverage.md
│   └── settings.json
├── reference/
│   ├── shogyouboki_kubun.pdf
│   ├── kogyoboki_kubun.pdf
│   ├── kamokuhyo.pdf
│   ├── SOURCES.md

│   └── accounts.yml

│   └── coverage.mjs
├── package.json
```

### 検証スクリプトは Node 単一ファイル・npm 依存なし

教材本体が「外部CDNを参照せずオフラインで動く」ことを要件にしている以上、検証側だけが依存を引き込むのは筋が通らない。

HTMLの解析に正規表現を使わない。131KBのHTMLから `.jnl` の借方・貸方を正規表現で取り出す実装は、ネストした表や属性順の揺れで必ず壊れる。かわりに Playwright で `file://` を開き、ページ内の DOM と JS ランタイムから読む。`Boki*.mount()` に渡された設定オブジェクト（正解科目・金額・answerインデックス）にも、この方法でのみ到達できる。

Playwright は Chromium を含めて既にローカルにある。

### 一次情報はリポジトリに固定する

出題区分表は2027年3月31日まで改定されない。この期間、区分表は変化しない一次情報なので、PDFをリポジトリに置き、そこから構造化データを起こす。

`reference/SOURCES.md` に取得元URL・取得日・PDF記載の改定日を残し、真正性を後から辿れるようにする。

### サブエージェントはプロジェクトスコープ

`.claude/agents/` に置き、ユーザーのグローバル設定には入れない。4体とも簿記教材専用で、他プロジェクトに出てくると邪魔になる。

## 3. CLAUDE.md

CLAUDE.md は毎セッション必ずコンテキストに載る。既存の3文書と内容が重複すると2箇所に散ってずれるため、**参照と分担**の方針を取る。

| 場所 | 内容 |
|---|---|
| `CLAUDE.md` | 3文書へのポインタ、検証コマンドの入口、最も高くつく地雷 |
| `教材制作ルール.md` | 執筆方針・共通アセットAPI・品質ゲートの定義 |
| `学習カリキュラム.md` | 週次計画・論点配分 |

CLAUDE.md に入れるのは次の5項目に限る。

1. **目的と締切** — 2026年11月15日 第174回。2027年4月の改定前に完了させる制約。これを知らないと、改定後の2027年度版を根拠に答えてしまう
2. **一次情報の所在** — 級の境界は `reference/syllabus.yml`、勘定科目は `reference/accounts.yml`。記憶で答えない
3. **教材を書くときは `教材制作ルール.md` を読む** — 全文は写さない
4. **公開前に `npm run verify` を通す** — 落ちたまま完了と報告しない
5. **地雷リスト** — 建設仮勘定=2級／伝票会計=3級だが出題対象／消費税・法人税等・貯蔵品・剰余金の配当=3級だが2級で必修／売上諸掛りの旧処理は削除済み

書かないもの：3文書の内容の複製、グローバルCLAUDE.mdに既にある原則、制作済み一覧（`教材制作ルール.md` の表が真実）。

### .claude/settings.json

`npm run verify` と `node tools/*.mjs` の実行を許可し、検証のたびに承認を求められない状態にする。

サブエージェントが検証を自走できることが前提の設計であり、そこで許可待ちが挟まると運用が止まる。逆に、教材ファイルの書き換えを伴う操作は既定のまま扱う。

## 4. サブエージェント

### boki-author — 単元HTMLの初稿

| | |
|---|---|
| 入力 | フェーズ・単元番号・扱う論点（区分表ID）・想定学習時間 |
| 出力 | 単元HTML 1枚 |
| ツール | Read / Write / Edit / Bash / Grep / Glob |
| モデル | Opus |

`教材制作ルール.md` の執筆方針に従う。`<meta name="boki-topics">` の記入は必須。共通アセットのクラスとAPIのみ使い、新しいCSSを足さない。

WebFetch を持たせない。オフライン動作が要件の教材に外部参照が混入する事故を、権限の設計で防ぐ。

### boki-drill — ドリル問題の量産

| | |
|---|---|
| 入力 | 論点・問題形式・問題数・難易度 |
| 出力 | `Boki*.mount()` に渡せる設定オブジェクト |
| ツール | Read / Write / Bash / Grep |
| モデル | Opus |

仕訳は貸借一致を自身で検算し、勘定科目は `accounts.yml` に実在するものに限る。`BokiNum` の設問には計算式メタを必ず持たせる（第6節）。

本文執筆と分けるのは、必要な思考が異なり、かつ問題作成は独立性が高く並列に回せるため。25問を1体に書かせるより 5問×5体のほうが速く、質のばらつきも小さい。

### boki-reviewer — 敵対的検証（品質ゲート8）

| | |
|---|---|
| 入力 | 単元HTMLのパスのみ |
| 出力 | 指摘（判定・根拠・該当箇所）＋ 自動修正した内容の列挙 |
| ツール | Read / Grep / Glob / Bash / Edit |
| モデル | Opus |

**執筆時の意図や修正履歴を渡さない。** 作成時の文脈から切り離すことが敵対的検証の前提であり、文脈を与えると「そう書いた理由」に引きずられて検証が甘くなる。

「誤りがある前提」で、会計処理の誤り・級の境界違反・ページ間の矛盾・本文に根拠のないドリル設問を洗う。

#### 自動修正してよい範囲

判定が一意に決まるものに限る。

- 貸借不一致。ただし正しい金額が本文の記述から一意に決まる場合のみ
- `BokiJournal` の正解科目が `accounts` プールに無い場合の、プールへの追加
- `BokiQuiz` の `answer` インデックスと解説の食い違い。解説が指す選択肢が一意なとき
- `.toc` のアンカーと `<h2 id>` の不一致、`<span class="num">` の番号飛び
- `accounts.yml` にない表記ゆれの、許容表記への修正

#### 報告のみ（修正しない）

- 会計処理そのものの誤り
- 級の境界の誤り
- 本文に根拠のないドリル設問
- ページ間の矛盾
- 説明の不足

級の境界を報告側に置くのは、その修正の実体が論点の追加・削除、すなわち単元の設計変更だからである。`.toc` のアンカー修正のような機械的操作とは性質が違う。

修正したときは、何をどう直したかを必ず出力に列挙する。黙って直さない。

### boki-coverage — カバレッジ検証（品質ゲート7）

| | |
|---|---|
| 入力 | フェーズまたは単元のパス |
| 出力 | 未カバー論点の一覧、扱いが不足している論点の指摘 |
| ツール | Read / Grep / Glob / Bash |
| モデル | Sonnet |

まず `tools/coverage.mjs` で meta と `syllabus.yml` の機械的な差分を取る。そのうえで「meta にはあるが本文の扱いが薄い論点」「到達チェックのN項目が必要十分か」という、機械では出せない判断を加える。

突き合わせが主で重い推論を要さないため Sonnet とする。

## 5. 一次情報の構造化

### syllabus.yml

出題区分表の全項目を、階層とIDを持つ構造に展開する。

PDFのテキストは3級・2級・1級が段組みで並び、列の開始位置で級が決まる（3級が桁0付近、2級が26付近、1級が52付近）。階層は行頭の記号（`第二` → `５．` → `ア．`）で判別する。行頭に記号がない行は前行の折り返しであり、独立項目ではない。

変換時の注意：2級の欄には、3級の項目の続きとして始まる行がある。行頭記号の有無と列位置の両方を見なければ、折り返しを独立項目と誤認する。

工業簿記の区分表は1ページに「2級/1級」の組を横に2つ並べる版面のため、商業簿記とは別の分割処理が要る。

各項目は以下を持つ。

```yaml
- id: 第二-5-ア
  section: 第二 諸取引の処理
  group: ５．手形
  title: 振出、受入、取立、支払
  grade: 3          # 3 | 2 | 1
  note: 営業外支払(受取)手形は2級・※付き
```

### accounts.yml

商業簿記標準・許容勘定科目表を、科目名・級・許容表記・区分（資産/負債/純資産/収益/費用）で構造化する。

これは当初の設計になかったが、区分表と同じページから取得できた。品質ゲート2を「プールに正解科目が入っているか」から「そもそも2級で使える科目名か」へ引き上げられる。

なお2級には3級の科目がすべて含まれる（PDF記載）。したがって2級の教材で使える科目は、2級欄と3級欄の和集合である。

## 6. 検証スクリプト

```
npm run verify                              # 全ページ
npm run verify phase0/01_3kyu-review.html   # 単一ページ
```

| # | 検査 | 判定方法 |
|---|---|---|
| 1 | 全仕訳の貸借一致 | 静的 `.jnl` の `.amt` を借方／貸方で合計。`BokiJournal` は `debit`／`credit` 配列を合計 |
| 2 | 正解科目が `accounts` プールに存在 | 各設問の正解科目 ⊆ プール |
| 2' | 科目名が `accounts.yml` に実在 | 標準・許容勘定科目表との照合 |
| 3 | `BokiNum` の解答を再計算 | 設問が持つ計算式メタを式パーサで評価し、`answer` と照合 |
| 4 | `BokiQuiz` の `answer` の妥当性 | インデックス範囲、および解説が言及する選択肢番号との整合 |
| 5 | `.toc` と見出しの整合 | アンカーと `<h2 id>`、`.num` の連番 |
| 6 | ランタイム検査 | JSエラー、id重複、`data-key` 重複、リンク切れ、420px幅での横スクロール |
| 7 | `boki-topics` メタ | 存在すること、IDが `syllabus.yml` に実在すること |

失敗は `ファイル:該当id 期待値 実際値` の形式で出力する。そのまま修正に使える粒度にするため。

### BokiNum の計算式メタ

`BokiNum` の解答を機械的に再計算するには、答えの数値だけでなく導出過程が要る。設問に計算式を持たせる。

```js
{ q: '...', answer: 12500, formula: '(50000 - 5000) * 0.25 + 1250' }
```

評価に `eval` は使わない。四則演算と括弧のみを受け付ける式パーサを `verify.mjs` に置く。教材のJSは自前で書くものであり任意コード実行の必要がない以上、実行系を持ち込む理由がない。

既存の Phase 0 の `BokiNum` 12問には `formula` がないため、遡って付与する。以降に作る設問では必須とし、`formula` のない `BokiNum` 設問は検証エラーとする。

## 7. 運用の流れ

```
単元を作る
  ├─ boki-author（本文）
  └─ boki-drill（問題）        ← 並列
        ↓
  npm run verify               ← ゲート1〜6、機械
        ↓
  ├─ boki-coverage（ゲート7）
  └─ boki-reviewer（ゲート8）  ← 並列
        ↓
  指摘の採否を判断 → 修正 → npm run verify 再走
```

機械的検査を先に通してからサブエージェントを呼ぶ。貸借不一致のような機械が見つけられる欠陥を残したままLLMに読ませるのは、コストの無駄であり、かつ本質的な指摘が些末な指摘に埋もれる。

指摘の採否は人間が決める。自動修正の対象は第4節に列挙した範囲に限られ、それ以外は報告に留まる。
