# 学習進捗の記録と書き出し 設計

作成日：2026年8月29日

一次情報をどこに置くかの決定と理由は [ADR-0001](../adr/0001-progress-tracking-source-of-truth.md) にある。本書は、その決定を前提に何をどう作るかを述べる。

## 1. 目的

教材を使いながら学習の実績が貯まり、それをリポジトリの `進捗ログ.md` へ運び出せる状態にする。

記録するものは4つ。単元の完了チェック、ドリルの正誤、学習時間、学習中のメモ。このうち完了チェックだけは既に動いており、残り3つは記録先がない。

学習者が記録のために行う操作は、メモを書くこと以外にない。チェック・正誤・時間はすべて教材を使う操作そのものから自動的に貯まる。

## 2. 全体構成

```
簿記2級教材/
├── progress.html            学習ダッシュボード（新規）
├── 進捗ログ.md               書き出し先（新規）
├── phase0/assets/app.js     BokiProgress を追加
├── tools/check.mjs          品質ゲート9を追加
└── .claude/skills/
    └── 進捗転記/SKILL.md      JSON を 進捗ログ.md へ転記する手順（新規）
```

データは `localStorage` の `boki2:progress` 1キーに集約する。教材ページは書き込むだけ、`progress.html` は読んで集計するだけ、という一方向にする。

## 3. データ構造

```js
{
  "version": 1,
  "sessions": [
    { "unit": "phase0/03_dentaku", "start": "2026-08-29T13:05:00+09:00", "sec": 2740 }
  ],
  "drills": {
    "phase0/03_dentaku#drill-teisu-1/q3": {
      "attempts": [
        { "at": "2026-08-29T13:22:00+09:00", "ok": false },
        { "at": "2026-08-29T13:24:00+09:00", "ok": true }
      ]
    }
  },
  "checks": {
    "phase0/04_junbi": { "moushikomi": true, "dentaku-kounyu": true }
  },
  "notes": [
    { "at": "2026-08-29T14:10:00+09:00",
      "unit": "phase0/02_kanjo-renrakuzu",
      "text": "アップストリームの非支配株主持分への按分が分からない" }
  ]
}
```

`version` は将来の構造変更に備える。読み込み時に想定より新しい `version` を見つけたら、変換を試みずそのまま保持し、ダッシュボードに警告を出す。壊れたデータを書き戻して失うより、読めないまま残すほうがよい。

### 単元キー

`phase0/03_dentaku` のように、拡張子を除いたパスを使う。

現在の `app.js` は `location.pathname.split('/').pop()` でファイル名だけを取っている。Phase 1 以降に `phase1/01_....html` ができると `phase0/01_3kyu-review.html` と衝突し、別単元の記録が混ざる。パス基準にしてこれを避ける。

### ドリルの粒度

設問単位で持ち、試行を配列で全部残す。

「最新の正誤」ではなく履歴にするのは、一発で正解した設問と3回目でようやく正解した設問を区別するためである。要復習リストの並び順はこの区別に依存する。

データ量は問題にならない。1設問1試行あたり約60バイト、11週間で全ドリルを3周しても数百KBに収まり、`localStorage` の 5MB に対して十分小さい。

### 学習時間

区間を「可視状態であり、かつ直近5分以内に操作があった時間」と定義して積算する。

経過時間をそのまま測ると、タブを開いたまま離席した時間が学習時間になる。実績が計画の23時間を上回っているように見えて、実際は足りていない、という最も避けたい壊れ方をする。

判定は `visibilitychange` と、`keydown` / `click` / `scroll` の最終時刻で行う。区間の確定は `visibilitychange`（非可視化）と `pagehide` で書き込む。`beforeunload` は Safari で発火しないことがあるため使わない。

### 既存データの移行

現在の `boki2:<page>:check` は、`boki2:progress` の初回読み込み時に `checks` へ取り込む。取り込み後も旧キーは消さない。消す利点がなく、移行に失敗した場合の復元手段が残る。

## 4. API

`app.js` に `BokiProgress` を追加し、`window` に公開する。

```js
BokiProgress.record(drillId, ok)   // ドリル1問の正誤
BokiProgress.check(unitKey, key, checked)
BokiProgress.note(text)
BokiProgress.dump()                // 全体を返す（ダッシュボード用）
BokiProgress.exportJSON()          // exportedAt を足した JSON 文字列
```

### 記録の呼び出しは app.js の内部で完結させる

単元HTMLの著者は記録用のコードを一切書かない。

`BokiJournal` / `BokiQuiz` / `BokiNum` / `BokiFill` の4つはいずれも内部に採点処理を持ち、既に `report(i, ok)` 相当の形で正誤を確定している。ここから `BokiProgress.record()` を呼ぶ。チェックリストは `initChecklists()` から呼ぶ。

単元HTMLは `boki-author` が量産するものであり、記録の呼び出しを著者の責務にすると、いずれ書き忘れが起きる。それが起きた週のデータは後から復元できない。`app.js` に閉じ込めれば、既存の phase0 の4単元も、これから書く単元も、著者側の変更なしに記録される。

### ドリルID

`mount(sel, cfg)` の `sel` が指す要素の `id` と、設問の添字から組み立てる。

```
phase0/03_dentaku#drill-teisu-1/q3
```

要素に `id` がない場合は記録しない。この検出は品質ゲート9で行う。

品質ゲート6が既に id 重複を検査しているため、ページ内での一意性は保証されている。

### メモ欄

単元HTMLに次を置くと、その位置に textarea と保存ボタンが生える。

```html
<div data-note></div>
```

既存の phase0 の4単元には追加が必要になる。以後は `boki-author` のテンプレートに含める。

## 5. ダッシュボード

`progress.html` をリポジトリ直下に置き、ルート `index.html` と `phase0/index.html` から導線を張る。

表示するもの：

- 今週の学習時間と、`学習カリキュラム.md` の週23時間に対する充足率
- 単元ごとの完了チェック数・学習時間・ドリル正答率
- 要復習リスト — 誤答を含むドリルを、直近の誤答が新しい順に並べる
- メモの一覧
- エクスポートボタン

要復習リストが、この画面の中心である。他はエクスポートすれば Claude 側でも読めるが、「次に何をやり直すべきか」だけは学習の最中に即座に見たい。

`progress.html` は集計するだけで、記録を書き換えない。唯一の例外は、明示的な全消去ボタンである。

## 6. エクスポート

`boki2:progress` の内容に `exportedAt` を足した JSON を、`navigator.clipboard.writeText()` でコピーする。全期間を毎回出力し、差分は取らない。

`exportedAt` を足すのは、受け取った側が記録の新しさを判断できるようにするためである。これがないと、古いエクスポートを貼り直したときに検出できない。

エクスポート形式を `localStorage` の構造と同一に保つことで、変換層がなくなり、両者がズレる余地がなくなる。

クリップボードAPIが使えない場合は、ボタンにその旨を表示するだけとする。代替手段は用意しない。

## 7. 転記

`.claude/skills/進捗転記/SKILL.md` に手順を置く。JSON を貼ると、Claude が次を行う。

1. `進捗ログ.md` の最終記録日を読む
2. それ以降の `sessions` / `drills` / `notes` を抽出する
3. 日付ごとに追記する（新しい日付が上）
4. 誤答が3回以上ある論点を要復習として明記する

エクスポートが全期間を含むため、どこから追記するかの判断はここで行う。ブラウザ側に「前回エクスポート時刻」を持たせない。ブラウザが持つと、`進捗ログ.md` を手で直したときに両者がズレる。

### 進捗ログ.md の形式

```markdown
# 学習記録

## 2026-08-29（金）
学習時間 2h56m（週計 2h56m / 目標 23h）

- phase0/03_dentaku 完了。定数計算は演算キー2回押しの機種だと確認
- 要復習: 勘定連絡図のアップストリーム按分
```

## 8. 品質ゲート9：進捗記録の健全性

`tools/check.mjs` に追加する。既存のゲートと同じく Playwright で `file://` を開いて検査する。

`教材制作ルール.md` のゲート7（カバレッジ）と8（敵対的検証）は判断が要るためサブエージェントが担う。ゲート9は機械的検査なので `npm run check` 側に入る。番号は続きだが、実行される場所は7・8と異なる。

| 検査 | 落とす条件 |
|---|---|
| 記録の配線 | ドリルを1問解いても `boki2:progress` の `drills` が増えない |
| ドリルID | `mount` のセレクタが指す要素に `id` がない |
| ダッシュボード | `progress.html` が JS エラーを出す |
| 堅牢性 | 壊れた JSON を `boki2:progress` に入れた状態で `progress.html` が例外を投げる |

記録の配線が切れても画面には何も現れない。気づくのは数週間後、進捗を出そうとして空だったときであり、その時点でデータは失われている。ゲート0が「ドリルが実際に mount されたか」を検査しているのと同じ理由で、機械的に検査する。

堅牢性の検査を入れるのは、`localStorage` が別ページや旧バージョンによって壊された状態でも、ダッシュボードが開かなければ復旧の手段がなくなるためである。
